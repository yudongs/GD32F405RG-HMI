# Grill Protocol（共享设计概念 / Grill Me）

> 在让人或 AI 大段写代码之前，先用 **Grill Me** 式追问对齐「看不见的共同理解」（分支、依赖、失败模式、回滚）。产出应可沉淀为 PRD、任务单或 Issue。
> 对应约束：`shared-design-concept`。

## 何时触发

- 新增或实质修改外设驱动（ADC/CAN/USART/SPI/I2C 等）时
- 修改中断处理逻辑或中断优先级时
- 新增板级配置（BSP）或修改引脚复用映射时
- 涉及多模块共享资源（时钟、DMA 通道、寄存器）时

## Owner

- **主持 Grill**：项目主程（固件架构负责人）
- **签字人**：需要至少一名主程确认设计结论
- **参与者**：涉及模块的 owner 需参与对齐

## 必问清单（可按项目扩充）

- 分支与边界条件是否穷举？
- 依赖哪些模块、服务或外部系统？
- 失败模式与可观测信号？
- 回滚或补偿路径？

## 输出落地位置

- `docs/plan/<feature>.md` — 特性设计文档
- 或 GitHub Issue / PR 描述章节
- 包含：分支穷举、依赖分析、失败模式、回滚方案

## 完成定义（Done）

- 主要分支与依赖已写入可追溯 artifact。
- 可拆解为任务单并评审通过。
- 相关术语已与 glossary 对齐或已登记新词。

## 反模式：Vibe loop

- 反复改规格提示词并全文重生成，对话不落地为 PRD/任务单。
- 未冻结公开接口就新增跨模块契约或顶层目录。

- 仅反复改规格再让模型生成全文、不沉淀对齐结论 → 迭代往往变差，库不可维护。
- 未对齐术语与边界就让模型新建跨模块类型或目录 → 放大混乱。
