# VTFP v1 Protocol Specification

**Version:** 0.1.0
**Status:** Draft (M1 implementation)
**Last updated:** 2026-06-06

## 1. Overview

The Virtual Test Fixture Protocol (VTFP) v1 is a request/response protocol
that runs over a shared RAM region between a PC (test agent) and an embedded
MCU (device under test). Communication is mediated by the MKLink serial
bridge: PC writes to the MCU's SRAM via `cmd.write_ram`, reads via
`cmd.read_ram`, and transfers large blocks via `cmd.dump_memory`.

VTFP is **domain-neutral** — it carries generic command IDs and a generic
state word, leaving all domain semantics (genset, PLC, inverter, ...) to
project-level `vtfp.yaml` definitions and codegen-produced handlers.

## 2. Wire Format

### 2.1 Shared RAM Layout

```
0x20000000 ┌──────────────────────────┐
           │  vtfp_header_t (44B)     │  ← control struct
0x2000002C ├──────────────────────────┤
           │  (RT-Thread resource info)│  ← optional, when USE_MKLINK_RESOURCE
0x20000040 ├──────────────────────────┤
           │  .vtfp_data (≥1KB)        │  ← command/response payload
           └──────────────────────────┘
```

The default header base is `VTFP_DEFAULT_RAM_BASE = 0x20000000`. Projects
may relocate via `vtfp.yaml` (`memory.header_base`), but the spec does not
allow splitting the header across non-contiguous addresses.

### 2.2 Header Layout (44 bytes, packed, little-endian)

| Offset | Size | Field       | Direction | Notes |
|--------|------|-------------|-----------|-------|
|   0    |  4   | `magic`     | both      | Must equal `VTFP_MAGIC` (`0x50465456`) |
|   4    |  2   | `version`   | both      | Must equal `VTFP_VERSION` (`0x0001`) |
|   6    |  2   | `features`  | MCU→PC    | Bit-OR of `VTFP_FEAT_*` |
|   8    |  4   | `command`   | PC→MCU    | Command ID; MCU clears to 0 after dispatch |
|  12    |  4   | `result`    | MCU→PC    | Result code; PC clears to 0 after read |
|  16    |  4   | `seq`       | PC→MCU    | Monotonic transaction counter |
|  20    |  4   | `param`     | PC→MCU    | Command-specific argument |
|  24    |  4   | `data_addr` | MCU→PC    | SRAM address of `.vtfp_data` |
|  28    |  4   | `data_len`  | both      | Valid bytes in data segment (≤ buffer size) |
|  32    |  4   | `flags`     | both      | Safety key (MCU), status bits |
|  36    |  4   | `checksum`  | PC→MCU    | CRC-32 of bytes [0..35] |
|  40    |  4   | `reserved`  | both      | MUST be 0 on wire |

**Total: 44 bytes.** Wire format is identical on C and Python sides; see
`c-tests/test_cross_lang.c` and `py/tests/test_cross_lang.py` for the
enforcement test.

### 2.3 Checksum

CRC-32 IEEE 802.3:
- polynomial: `0xEDB88320` (reflected form of `0x04C11DB7`)
- init: `0xFFFFFFFF`
- refin/refout: `True`
- xorout: `0xFFFFFFFF`
- check value: `CRC32("123456789") = 0xCBF43926`

Coverage: bytes [0..35] of the header (everything before `checksum` and
`reserved`). The reserved field is not covered; it MUST be 0.

## 3. Command ID Partition

| Range      | Purpose                          | Examples |
|------------|----------------------------------|----------|
| 0x01..0x0F | User-defined (domain commands)   | SET_PARAM, TOGGLE_OUT, ... |
| 0x10..0x1F | VTFP standard                    | QUERY_INFO, QUERY_STATE, RESET, HEARTBEAT |
| 0xF0..0xFF | Safety / control                 | ARM, DISARM |

Implementations MUST reject command IDs outside the partition map with
`VTFP_R_UNKNOWN_CMD` (0xFF).

### 3.1 Standard Commands

| ID    | Name           | Direction | Requires ARM | Response schema |
|-------|----------------|-----------|--------------|-----------------|
| 0x10  | `QUERY_INFO`   | PC→MCU    | No           | `{product_id: str, fw_version: str, protocol_version: uint16, features: uint16}` |
| 0x11  | `QUERY_STATE`  | PC→MCU    | No           | 8-byte opaque state word |
| 0x12  | `RESET`        | PC→MCU    | **Yes**      | none |
| 0x13  | `HEARTBEAT`    | PC→MCU    | No           | none |
| 0xFE  | `ARM`          | PC→MCU    | No (itself)  | none |
| 0xFF  | `DISARM`       | PC→MCU    | No           | none |

User-defined commands (0x01..0x0F) are declared in `vtfp.yaml` and their
schemas are generated by the M4 scaffolding tool.

### 3.2 Result Codes and Namespace Convention

The MCU writes a single 8-bit result code to `header.result` for every
command. The set of legal values is:

| Code   | `VTFP_R_*` (canonical) | `VTFP_OK` / `VTFP_ERR_*` (alias) | Meaning |
|--------|------------------------|----------------------------------|---------|
| `0x00` | `VTFP_R_OK`            | `VTFP_OK`                        | Success |
| `0x01` | `VTFP_R_NOT_ARMED`     | `VTFP_ERR_NOT_ARMED`             | Command requires ARM, but no ARM is active |
| `0x02` | `VTFP_R_ARM_EXPIRED`   | `VTFP_ERR_ARM_EXPIRED`           | ARM window expired before command issued |
| `0x03` | `VTFP_R_SAFETY_KEY`    | `VTFP_ERR_SAFETY_KEY`            | ARM `param` did not match `VTFP_SAFETY_KEY` |
| `0x04` | `VTFP_R_PARAM_RANGE`   | `VTFP_ERR_PARAM_RANGE`           | `param`/payload out of accepted range |
| `0x05` | `VTFP_R_NOT_INIT`      | `VTFP_ERR_NOT_INIT`              | Subsystem referenced by command not initialised |
| `0x06` | `VTFP_R_BUF_OVERFLOW`  | `VTFP_ERR_BUF_OVERFLOW`          | Handler tried to write beyond `data_len` |
| `0xFF` | `VTFP_R_UNKNOWN_CMD`   | `VTFP_ERR_UNKNOWN_CMD`           | Command ID not in any partition |

**Namespace convention.** Two parallel namespaces for result codes
coexist in the v0.1.0 headers:

- `VTFP_OK` / `VTFP_ERR_*` — defined in [`c-types/vtfp_header.h`](c-types/vtfp_header.h).
  These were the first names declared, in order to give the struct
  definition a self-contained set of result constants.
- `VTFP_R_*` — defined in [`c-types/vtfp_result.h`](c-types/vtfp_result.h).
  These are byte-for-byte re-declarations of the same numeric values,
  introduced during the M1-T3 review so that the result namespace is
  isolated in its own header.

The two namespaces **MUST** remain numerically identical for the lifetime
of v1.x. **The `VTFP_R_*` namespace is canonical** for all new code —
codegen output, M2 firmware handlers, M3 Python SDK, and tests should
prefer `VTFP_R_*`. The `VTFP_OK` / `VTFP_ERR_*` aliases are retained for
backward compatibility with the pre-existing GEC6100D `test_fixture.h`
callers and MUST NOT be removed in v1.x.

## 4. ARM Safety Protocol

The ARM mechanism protects dangerous operations (mode change, parameter
write, remote start, ...). It is **mandatory** for any command flagged
`requires_arm: true` in `vtfp.yaml`.

### 4.1 Sequence

1. PC issues `VTFP_CMD_ARM` with `param = VTFP_SAFETY_KEY` (`0xAA55AA55`)
2. MCU validates the key. If valid, sets `arm_tick = now()`
3. `arm_tick` is valid for `VTFP_ARM_TIMEOUT_MS` (default `2000` ms)
4. PC issues the dangerous command within the window
5. MCU executes it, then (if `auto_disarm` is enabled) clears `arm_tick`
6. Subsequent dangerous commands require a fresh `ARM`

### 4.2 Failure Modes

- **Wrong safety key** → `VTFP_R_SAFETY_KEY`
- **Command issued without ARM** → `VTFP_R_NOT_ARMED`
- **ARM window expired** → `VTFP_R_ARM_EXPIRED`

## 5. Data Segment

For commands with payloads > 0 bytes, the payload is written to
`.vtfp_data` before the command word is set, and read after the result
word is observed:

```
PC:  write data_addr..data_addr+data_len  (payload)
PC:  write data_len in header
PC:  write seq, param, command in header
PC:  poll header.result (timeout = 2s)
PC:  if result == OK: read data_addr..data_addr+data_len
```

The data segment is project-defined (default 1024 bytes). Buffers larger
than `data_len` are not guaranteed; payloads MUST fit. MCU returns
`VTFP_R_BUF_OVERFLOW` if the handler attempts to write beyond the buffer.

## 6. Versioning

`VERSION` follows SemVer. The protocol is forward-compatible within MAJOR
version: a v0.1.0 PC may talk to a v0.3.0 MCU but the converse is not
guaranteed. PC SDK MUST check `header.version` and warn on mismatch.
